# STREAMING.md — Torrent + FFmpeg + HLS

## 1. Цель

Начать playback до полной загрузки медиафайла.

Torrent engine может использовать ограниченный временный cache. Строгий режим без записи медиа на диск требует отдельного PoC и не должен считаться гарантированной возможностью до проверки выбранного engine и всей цепочки обработки.

Streaming subsystem должен быть независимым от web-интерфейса. Один и тот же playback API должен поддерживать текущий web-клиент и будущие клиенты, включая Android TV.

Основная архитектура:

- Rust — управление сессиями, orchestration, HTTP API и контроль ресурсов.
- Tokio — асинхронный I/O, управление задачами и отмена операций.
- Torrent engine — получение metadata, выбор файла, загрузка необходимых частей и предоставление доступа к данным.
- FFprobe — инспекция контейнера, потоков, кодеков и характеристик медиа.
- FFmpeg — remux, stream copy, transcoding и генерация HLS.
- HLS — основной кандидат для первоначального web playback.
- Intel integrated graphics с VA-API — основной вариант аппаратного ускорения на поддерживаемых Linux-хостах.
- Software transcoding — fallback при недоступности или несовместимости аппаратного ускорения.

Приоритеты:

1. Не загружать весь файл до начала playback.
2. Использовать stream copy или remux, когда это совместимо с источником и клиентом.
3. Выполнять transcoding только при необходимости.
4. Поддерживать ограниченные ресурсы, отмену операций и гарантированную очистку.
5. Поддерживать seeking там, где это позволяют источник, torrent engine и выбранная схема потоковой передачи.
6. Подтверждать заявленные возможности тестами, а не предположениями об API библиотек и поведении FFmpeg.

Поддерживать только источники, доступ к которым пользователь имеет право получать и передавать.

## 2. Основные принципы

1. Не загружать целый медиафайл до начала playback.
2. Предпочитать remux или stream copy, если исходные потоки совместимы с целевым форматом и клиентом.
3. Transcode использовать только при необходимости из-за кодеков, контейнера, аудио, субтитров, требований клиента или ограничений streaming pipeline.
4. Ограничивать память, дисковое пространство, количество сессий, соединений и время выполнения операций.
5. Поддерживать seeking, если source adapter и torrent engine обеспечивают необходимые диапазоны байтов или медиаданные.
6. Останавливать фоновую работу после завершения, отмены или истечения срока действия playback-сессии.
7. Не считать stdin pipe универсальным способом передачи произвольных MKV и MP4: контейнеры могут требовать произвольного доступа к данным.
8. Не считать поддержку VA-API гарантией поддержки конкретного кодека, профиля, bit depth или разрешения.
9. Не считать аппаратное ускорение активным только потому, что установленный FFmpeg содержит VA-API. Проверять инициализацию устройства и выполнение репрезентативной операции.
10. Не запускать повторные FFmpeg-процессы для одной активной сессии при каждом запросе playlist или segment, если это явно не предусмотрено архитектурой.
11. Не использовать неограниченные очереди и фоновые Tokio-задачи для пользовательских запросов.
12. Не передавать пользовательские строки в shell-команды.
13. Не принимать произвольные FFmpeg flags, executable paths или URL от клиента.
14. Не считать обнаружение источника подтверждением права на его использование.
15. Не логировать секретные URL, bearer tokens, credentials и полные magnet URI по умолчанию.
16. При ошибках возвращать различимые причины отказа, не маскируя их под общую ошибку playback.
17. Любые заявленные возможности torrent engine, FFmpeg и аппаратного ускорения подтверждать тестами на поддерживаемой конфигурации.

## 3. Общая streaming pipeline

Предполагаемый процесс:

1. Клиент выбирает результат поиска и источник.
2. Backend проверяет источник и создаёт playback-сессию.
3. Source adapter разрешает источник, получает torrent metadata при необходимости и определяет выбранный файл.
4. Source adapter предоставляет доступ к медиаданным по мере их появления.
5. Media subsystem определяет контейнер, размер, потоки, кодеки, длительность и доступность seeking.
6. Playback planner выбирает stream copy, remux или transcoding.
7. FFmpeg формирует HLS playlist и сегменты либо используется другая проверенная стратегия доставки.
8. Клиент запрашивает playlist и сегменты по HTTP.
9. Backend отслеживает состояние сессии, доступность источника и использование ресурсов.
10. При остановке, истечении срока действия или ошибке backend завершает дочерние процессы и освобождает ресурсы сессии.

Source adapter не должен раскрывать детали реализации torrent engine слою HTTP API.

Интерфейс source adapter должен предоставлять необходимые операции и состояние источника независимо от конкретной библиотеки:

- Получение metadata.
- Перечисление файлов.
- Выбор файла.
- Получение размера и доступности данных.
- Чтение данных по смещению, если поддерживается.
- Ожидание доступности требуемого диапазона данных.
- Отмена ожидающих чтений.
- Остановка загрузки при завершении сессии.
- Получение прогресса и ошибок.
- Контроль cache и ограничений ресурсов.

Конкретные названия методов и API зависят от выбранного engine и должны быть подтверждены его документацией и PoC.

## 4. Torrent engine ADR

До выбора torrent engine подготовить ADR (Architecture Decision Record) и обязательный PoC.

Оценить:

- Зрелость библиотеки и активность разработки.
- Наличие поддерживаемого Rust API.
- Качество документации и примеров.
- Возможность интеграции с Tokio и асинхронным I/O.
- Получение torrent metadata без загрузки всего содержимого.
- Выбор отдельного файла в многофайловом torrent.
- Приоритизацию выбранного файла и необходимых частей.
- Random access и seeking.
- Возможность чтения данных по смещению.
- Модель временного cache и ограничения дискового пространства.
- Возможность минимизировать или полностью исключить запись медиа на диск.
- DHT, tracker и peer support.
- Поведение при отсутствии peers, медленных peers и изменении доступности источника.
- Таймауты, отмену запросов и завершение фоновой загрузки.
- Ограничения количества соединений и скорости, если engine это поддерживает.
- Ограничения памяти, CPU и дисковых операций.
- Поддерживаемые архитектуры и multi-arch deployment.
- Лицензию библиотеки и её зависимостей.
- Возможность контролируемого завершения сессии и очистки ресурсов.
- Метрики прогресса, доступности данных и ошибок.
- Поведение после рестарта процесса.

Если зрелой Rust-библиотеки с необходимыми возможностями не хватает, допускается рассмотреть изолированный компонент на другом языке или отдельный процесс. Такое решение требует обоснования в ADR, описания IPC, границ безопасности, контроля ресурсов, отмены операций и поведения при аварийном завершении.

Не добавлять отдельный компонент только ради обхода ограничений без измеримого преимущества.

### 4.1. Обязательный PoC

Проверить на собственном или разрешённом тестовом материале:

- Получение torrent metadata.
- Перечисление файлов и детерминированный выбор файла в многофайловом torrent.
- Начало чтения до полной загрузки файла.
- Приоритизацию выбранного файла.
- Буферизацию необходимых частей для старта.
- Доступность диапазонов байтов, требуемых медиапарсером.
- Random access и seek.
- MP4 и MKV отдельно.
- HLS remux с сохранением исходных кодеков, когда это возможно.
- Transcode fallback.
- Time-to-first-frame и time-to-first-playable-segment.
- Остановку чтения и загрузки при отмене сессии.
- Очистку временных файлов и cache.
- Поведение при медленных и недоступных peers.
- Поведение при исчезновении peers во время чтения.
- Ограничение памяти, дискового cache и количества соединений.
- Восстановление после ошибки источника.
- Работу нескольких одновременных сессий.

Для каждого теста зафиксировать исходный материал, конфигурацию, ожидаемое поведение, фактический результат, время выполнения и ограничения.

Не считать успешный запуск на одном файле доказательством поддержки произвольных MKV и MP4.

### 4.2. Random access и чтение по смещению

Контейнеры MP4 и MKV могут требовать metadata или медиаданные из позиций, отличных от начала файла.

Нельзя полагаться на последовательный stdin pipe, если выбранный формат и проверенный playback path явно не поддерживают такие ограничения.

Предпочтительна абстракция источника, которая поддерживает чтение по смещению, либо локальное sparse/cache-backed представление файла, если выбранный engine обеспечивает такую возможность.

Реализация должна различать:

- Байты, уже доступные локально.
- Байты, которые сейчас загружаются.
- Байты, недоступные из-за остановившегося или неполного источника.
- Некорректное смещение.
- Конец файла.
- Отмену чтения.
- Таймаут чтения.
- Необратимую ошибку источника.

Если источник не поддерживает произвольный доступ, явно указывать это ограничение и выбирать совместимый playback path либо возвращать понятную ошибку.

### 4.3. Буферизация и приоритизация

Torrent engine должен обеспечивать получение данных, необходимых для начала воспроизведения, без ожидания полной загрузки выбранного файла.

Требования:

- Приоритизировать выбранный файл, если engine поддерживает такую возможность.
- Запрашивать данные, необходимые для определения структуры медиа и запуска выбранного playback path.
- Учитывать, что медиапарсеру могут понадобиться данные из разных частей файла.
- Не считать линейное получение первых байтов достаточным условием для готовности.
- Ограничивать размер буфера и количество ожидающих чтений.
- Учитывать отменённые и устаревшие запросы.
- Не удерживать ресурсы бесконечно, если нужные части недоступны.
- Не допускать, чтобы один медленный источник блокировал независимые сессии.

Размер стартового буфера должен быть конфигурируемым или определяться проверенной стратегией. Не задавать универсальное значение без измерений.

### 4.4. Работа при недоступности peers

Если нужные части недоступны:

- Оставаться в состоянии buffering до установленного таймаута.
- Отслеживать прогресс и доступность источника.
- Не запускать бесконечные повторные попытки.
- Прекращать зависшие операции по таймауту.
- Возвращать различимую ошибку, если продолжение playback невозможно.
- Корректно отменять FFmpeg, если его вход больше не может обеспечиваться.
- Сохранять только ограниченную диагностическую информацию.
- Освобождать временные ресурсы после остановки или истечения срока действия сессии.

## 5. Media inspection и playback planning

Использовать FFprobe или другой проверенный инструмент для определения:

- Формата контейнера.
- Наличия видео- и аудиопотоков.
- Видеокодека.
- Профиля видеокодека.
- Pixel format и bit depth.
- Разрешения.
- Частоты кадров, если доступна.
- Аудиокодека.
- Количества аудиоканалов и channel layout.
- Частоты дискретизации.
- Длительности, если она известна.
- Наличия встроенных субтитров.
- Доступных потоков и их идентификаторов.
- Пригодности медиа для выбранного output path.
- Ограничений seeking, выявленных источником и используемым pipeline.

Инспекция должна иметь ограниченное время выполнения и не требовать загрузки всего файла.

FFprobe должен работать с тем же контролируемым доступом к источнику, что и FFmpeg. Не предполагать, что FFprobe сможет читать torrent source напрямую.

Если инспекция требует произвольного доступа, это должно поддерживаться source adapter либо проверенной промежуточной cache-backed реализацией.

До запуска долгоживущего FFmpeg-процесса создать playback plan.

План должен определять:

- Выбранный видео- и аудиопоток.
- Требуется ли remux или stream copy.
- Требуется ли transcoding.
- Какие кодеки и контейнеры будут использоваться.
- Нужна ли аппаратная обработка.
- Допустим ли software fallback.
- Как будет организован HLS output.
- Какой тип playlist требуется.
- Какие ограничения применяются к seeking.
- Какие временные файлы создаются.
- Каковы лимиты времени и ресурсов для операции.

### 5.1. Direct stream copy / remux

Использовать stream copy, когда исходные потоки можно упаковать в выбранный output format и они совместимы с целевым клиентом.

Stream copy не требует декодирования и повторного кодирования видео. Это предпочтительный вариант при совместимости источника и pipeline.

Однако совместимость должна быть подтверждена с учётом:

- Видеокодека и его профиля.
- Аудиокодека и channel layout.
- Ограничений целевого клиента.
- Timestamp и временных меток.
- Ограничений контейнера.
- Границ сегментов.
- Доступности исходных данных.
- Поддержки выбранного HLS segment format.
- Возможности корректно завершать и публиковать сегменты.

Не предполагать, что любой MP4 или MKV можно преобразовать в HLS без дополнительной обработки.

При несовместимости не повторять один и тот же заведомо неподходящий remux бесконечно. Playback planner должен выбрать разрешённый fallback или вернуть диагностируемую ошибку.

### 5.2. Transcoding

Выполнять transcoding только при необходимости.

Возможные причины:

- Неподдерживаемый видеокодек.
- Неподдерживаемый аудиокодек.
- Несовместимый профиль, pixel format или bit depth.
- Ограничения браузера или Android TV.
- Требуемое изменение разрешения.
- Требуемое преобразование формата.
- Невозможность корректно упаковать исходные потоки в выбранный HLS pipeline.
- Необходимость обработки субтитров, если включено их отображение через burn-in.

Использовать Intel VA-API для поддерживаемого аппаратного декодирования, фильтрации и/или кодирования, когда это улучшает pipeline и поддерживается установленным FFmpeg и конкретным GPU.

Использовать software processing, когда аппаратная обработка недоступна, несовместима или не подходит для выбранной операции.

Не считать аппаратное ускорение гарантированно более быстрым для каждой операции.

Избегать лишних передач между GPU memory и system memory. Если hardware decode не может эффективно передать кадры в последующую обработку, сравнить такой pipeline с software path.

### 5.3. Планирование fallback

При невозможности использовать выбранный playback mode:

1. Зафиксировать причину отказа.
2. Проверить, допускает ли сессия другой режим.
3. При необходимости перейти с remux на transcoding.
4. Если включён `HWACCEL_MODE=auto`, попробовать проверенный software fallback.
5. Если операция требует аппаратного ускорения и включён strict mode, завершить операцию с понятной ошибкой.
6. Не оставлять предыдущий FFmpeg-процесс или временные файлы активными после перехода на другой режим.

Не выполнять fallback, который нарушает заданные ограничения сессии или ресурсов.

## 6. Intel VA-API

Intel iGPU с VA-API является основной целью аппаратного ускорения на поддерживаемых Linux-хостах.

Аппаратное ускорение не является обязательным условием работы всего сервиса: хост без `/dev/dri` должен поддерживать software mode, если остальные требования к ресурсам соблюдаются.

### 6.1. Конфигурация

Поддержать следующие значения:

- `HWACCEL_MODE=auto` — попытаться использовать проверенный аппаратный путь и перейти на software processing, если это допускается политикой.
- `HWACCEL_MODE=vaapi` — запросить VA-API. При недоступности устройства или несовместимости операции применить документированную политику strict mode.
- `HWACCEL_MODE=software` — отключить аппаратное ускорение.

Дополнительные параметры:

- `VAAPI_DEVICE` — путь к DRM render node, обычно `/dev/dri/renderD128`.
- `HWACCEL_REQUIRED=false` — если `true`, завершать playback с ошибкой, когда требуемая операция аппаратной обработки недоступна.

`HWACCEL_REQUIRED` должен иметь однозначную семантику. Если аппаратная обработка не требуется конкретным playback plan, её недоступность сама по себе не должна ломать совместимый stream copy.

Путь к устройству должен задаваться конфигурацией. Не предполагать, что на всех хостах используется один и тот же render node.

### 6.2. Проверка аппаратного ускорения

При запуске или во время диагностики проверять:

1. Существует ли настроенный device node.
2. Имеет ли пользователь сервиса права доступа.
3. Содержит ли установленная сборка FFmpeg поддержку VA-API.
4. Доступны ли требуемые VA-API encoders и filters.
5. Удаётся ли инициализировать устройство.
6. Успешно ли выполняется репрезентативная операция для требуемого кодека и pixel format.
7. Поддерживает ли устройство требуемый профиль, разрешение и bit depth.

`vainfo` можно использовать как дополнительный диагностический инструмент, если он установлен. Сам факт успешного выполнения `vainfo` не подтверждает работоспособность конкретного FFmpeg pipeline.

Возможности зависят от поколения GPU, драйвера, сборки FFmpeg, профиля кодека, bit depth и разрешения. Проверять именно ту операцию, которая требуется выбранному playback plan.

Не сообщать, что hardware acceleration активно, если проверена только доступность библиотеки или перечисление энкодеров. Успешная инициализация и репрезентативная обработка должны подтверждаться отдельно.

### 6.3. Пример диагностической VA-API-команды

Пример для доступного локального входного файла. Это диагностический пример, а не универсальная production-команда:

```bash
ffmpeg \
  -vaapi_device /dev/dri/renderD128 \
  -i input.mkv \
  -vf 'format=nv12,hwupload,scale_vaapi=w=1280:h=720' \
  -c:v h264_vaapi \
  -c:a aac \
  -f hls \
  -hls_time 4 \
  -hls_list_size 0 \
  output.m3u8
```

Команда может требовать корректировки с учётом:

- Входного pixel format.
- Сборки FFmpeg.
- Поддерживаемого GPU.
- Аудиопотоков.
- Timestamp.
- HLS segment format.
- Требований целевого клиента.
- Выбранного режима декодирования и кодирования.

Не копировать пример в production без тестирования.

В production FFmpeg arguments должны формироваться из валидированной конфигурации и проверенных media metadata. Не интерполировать пользовательские строки в shell-команду.

### 6.4. Hardware acceleration fallback

При `HWACCEL_MODE=auto`:

- Проверить доступность устройства и требуемых возможностей.
- Запустить только проверенный hardware path.
- Обнаружить ошибку инициализации или выполнения.
- При допустимости повторить операцию в software mode.
- Убедиться, что предыдущий процесс завершён и ресурсы освобождены.
- Зафиксировать фактически выбранный режим и причину fallback.

При `HWACCEL_MODE=software` аппаратное ускорение не использовать.

При `HWACCEL_MODE=vaapi` и `HWACCEL_REQUIRED=true` операция, требующая недоступной аппаратной обработки, должна завершаться понятной ошибкой. Не маскировать отказ незаметным переходом на CPU.

Политика fallback должна быть согласована с API и отражаться в состоянии сессии.

## 7. HLS output

Основной кандидат для первоначального web playback — HLS.

Примеры возможных endpoint:

- `GET /api/v1/playback/{session_id}/master.m3u8`
- `GET /api/v1/playback/{session_id}/index.m3u8`
- `GET /api/v1/playback/{session_id}/segments/{segment_name}`

Фактические пути должны соответствовать `API.md` и OpenAPI specification. Эти примеры не разрешают создавать конфликтующие определения endpoint.

Playlist и segment implementation должны:

- Формировать корректный HLS playlist.
- Использовать стабильные идентификаторы сегментов в пределах сессии.
- Возвращать правильные Content-Type.
- Не допускать path traversal и произвольного доступа к файлам.
- Обрабатывать запросы сегментов, которые ещё не готовы.
- Не раскрывать клиенту внутренние filesystem paths.
- Проверять принадлежность сессии и правила доступа либо access token.
- Прекращать обслуживание истёкших и удалённых сессий.
- Безопасно удалять устаревшие сегменты.
- Обрабатывать ошибки запуска FFmpeg и преждевременное завершение процесса.
- Не допускать неограниченного накопления готовых сегментов.
- Учитывать отмену сессии во время HTTP-запроса.
- Не выдавать клиенту некорректный или частично записанный сегмент как готовый.

Выбирать live-style или VOD-style поведение playlist в соответствии с реальной стратегией потоковой передачи.

Не помечать playlist как VOD, если реализация не может предоставить соответствующее полное медиапредставление.

### 7.1. Публикация playlist и сегментов

FFmpeg должен записывать результаты в выделенную директорию сессии.

Backend должен отличать:

- Сегмент ещё не создан.
- Сегмент записывается.
- Сегмент готов к выдаче.
- Сегмент удалён.
- Сегмент недоступен из-за завершения или ошибки процесса.

Клиент не должен получать частично записанный файл как завершённый сегмент.

Способ определения готовности должен соответствовать выбранному FFmpeg output mode и проверяться тестами.

Не считать появление playlist достаточным условием готовности playback: initial playable segment также должен существовать и быть доступен.

### 7.2. HTTP-доступ и безопасность

Обработчики playlist и segment должны проверять:

- Существует ли сессия.
- Разрешён ли запрашивающему доступ к сессии.
- Не истекла ли сессия.
- Не находится ли сессия в состоянии stopping, stopped, failed или expired.
- Принадлежит ли имя сегмента выделенной директории сессии.
- Допустим ли формат идентификатора сегмента.
- Не запрашивается ли произвольный путь через манипуляции с именем файла.

Не использовать клиентский `session_id` как единственную гарантию авторизации, если API предусматривает более строгие правила владения сессией.

Не раскрывать реальные пути, внутренние torrent metadata и peer addresses в HTTP-ответах без необходимости.

## 8. Startup buffering и playback readiness

Playback-сессия должна иметь явные состояния.

Минимальная модель:

- `created`
- `resolving`
- `buffering`
- `ready`
- `playing`
- `stopping`
- `stopped`
- `failed`
- `expired`

Требуемые переходы и их публичное представление должны быть задокументированы в `API.md`.

Семантика состояний:

- `created` — сессия создана, но разрешение источника ещё не завершено.
- `resolving` — выполняется разрешение источника, получение metadata или выбор файла.
- `buffering` — получаются данные, необходимые для инспекции и запуска playback.
- `ready` — playlist и initial playable segment доступны и прошли проверку.
- `playing` — клиент начал playback либо backend получил определённый системой сигнал начала воспроизведения.
- `stopping` — выполняется отмена задач, завершение процессов и очистка.
- `stopped` — завершение сессии и освобождение ресурсов подтверждены.
- `failed` — операция завершилась ошибкой.
- `expired` — сессия завершена политикой срока действия.

Если backend не может достоверно определить факт начала воспроизведения на клиенте, он не должен выдавать `playing` за подтверждённый факт декодирования кадров. В таком случае состояние означает только определённый backend-сигнал активности, описанный в API.

Не помечать сессию `ready` только потому, что FFmpeg успешно запущен.

Необходимо подтвердить, что:

- FFmpeg не завершился с ошибкой.
- Ожидаемый playlist создан и валиден.
- Initial playable segment доступен.
- Сегмент завершён и может быть выдан клиенту.
- Источник способен предоставить необходимые данные для выбранного режима.

Startup process должен иметь конфигурируемые таймауты.

Если источник не предоставляет достаточно данных, вернуть понятную ошибку и завершить связанные процессы и задачи.

Backend должен различать:

- Недоступность источника.
- Недостаточную буферизацию.
- Неподдерживаемый формат медиа.
- Ошибку FFprobe.
- Ошибку запуска или выполнения FFmpeg.
- Ошибку инициализации VA-API.
- Исчерпание ресурсных лимитов.
- Таймаут операции.

### 8.1. Time-to-first-frame

Измерять отдельно:

- Время разрешения источника.
- Время получения metadata.
- Время буферизации.
- Время запуска FFprobe.
- Время запуска FFmpeg.
- Время до появления первого валидного playlist.
- Время до появления первого playable segment.
- Time-to-first-frame, если он может быть достоверно измерен на уровне клиента или тестового плеера.

Time-to-first-playable-segment не является автоматически равным time-to-first-frame. На итог влияют загрузка сегмента, сетевые задержки, инициализация декодера и особенности плеера.

Использовать тестовый клиент для измерения полного времени до первого кадра.

## 9. Seeking

Seeking требует координации между плеером, HLS-сессией, FFmpeg и source adapter.

Не считать возможность чтения произвольных байтов полной гарантией успешного seeking в HLS. Также учитывать timestamp, структуру контейнера, границы сегментов и возможность получить нужные части источника.

Проверить:

- Seek вперёд к уже буферизованной позиции.
- Seek вперёд к данным, которые ещё не доступны.
- Seek назад к закешированным данным.
- Seek после удаления соответствующего сегмента.
- Seek при медленном или недоступном источнике.
- Отмену устаревших seek-операций.
- Очистку заброшенных FFmpeg-процессов и временных файлов.
- Повторный seek во время выполнения предыдущего.
- Корректность timestamp и воспроизведения после seek.
- Поведение клиента, когда целевая позиция не может быть обеспечена источником.

Первоначальная реализация может ограничивать seeking, если выбранный torrent engine или streaming design не поддерживает его надёжно.

Такие ограничения должны быть явно отражены в API и документации клиента.

Если seek требует нового FFmpeg-процесса или отдельного playback pipeline, реализация должна корректно отменять предыдущие операции и контролировать количество одновременно выполняющихся процессов.

## 10. Аудио и субтитры

Первоначально сохранять поддерживаемые аудиопотоки, если это возможно.

Если аудио требует transcoding, выбирать кодек, поддерживаемый целевым клиентом и выбранной HLS-конфигурацией.

Не предполагать, что все клиенты принимают одинаковые аудиокодеки и channel layout.

Поддержка субтитров должна иметь явно определённый scope.

Первая версия может:

- Определять и возвращать metadata встроенных subtitle streams.
- Не поддерживать их визуальное отображение.
- Добавить поддержку выбранных типов субтитров отдельным этапом.

Если субтитры будут встраиваться в видеокадры через burn-in, учитывать дополнительные затраты CPU/GPU и необходимость декодирования и повторного кодирования видео.

Не отбрасывать запрошенные аудио- или subtitle tracks без объяснения. Возвращать metadata доступных потоков, чтобы клиент мог сделать информированный выбор.

Если конкретный track невозможно воспроизвести, сообщать об ограничении, а не подменять его другим потоком без согласованного поведения API.

## 11. Временное хранилище и очистка

Все временные данные должны храниться в выделенной конфигурируемой директории.

Требования:

- Явный максимальный размер общего cache.
- Явный лимит cache на сессию.
- Уникальные, непредсказуемые директории сессий.
- Запрет на использование клиентского пути как filesystem path.
- Учёт всех файлов и дочерних процессов, созданных сессией.
- Удаление артефактов после успешной остановки или истечения срока действия.
- Ограниченное хранение диагностической информации.
- Запрет на удаление файлов, которые ещё читаются активными сессиями.
- Очистка заброшенных временных данных после перезапуска сервиса.
- Контроль дискового пространства во время активных сессий.
- Безопасное удаление файлов при ошибке FFmpeg.
- Очистка временных данных после неудачного разрешения источника.
- Отсутствие неконтролируемого превращения cache в постоянную медиатеку.

Не считать удаление директории достаточной очисткой, если процессы или фоновые задачи продолжают использовать её.

### 11.1. Cache policy

Cache policy должна определять:

- Максимальный размер общего cache.
- Максимальный размер cache одной сессии.
- TTL временных данных.
- Правила удаления устаревших данных.
- Поведение при достижении лимита.
- Поведение при нехватке дискового пространства.
- Приоритет активных сессий над неактивными данными.
- Правила безопасного удаления сегментов, которые больше не нужны.
- Обработку файлов, занятых активными операциями.

Не удалять необходимые активной сессии данные без согласованной политики.

Если для продолжения playback требуется больше места, чем разрешено лимитами, не расширять cache бесконтрольно. Вернуть контролируемую ошибку либо применить проверенную стратегию освобождения безопасно удаляемых данных.

### 11.2. Режим без записи на диск

Строгий режим без записи медиа на диск требует отдельного PoC.

Необходимо различать:

- Отсутствие постоянного хранения медиатеки.
- Ограниченный временный disk cache.
- Использование временных HLS-сегментов.
- Полное отсутствие записи медиаданных на дисковые устройства.

Это разные гарантии.

Нельзя заявлять, что система не записывает медиа на диск, если FFmpeg, torrent engine, ОС или файловая система могут создавать временные файлы.

До подтверждения PoC основная архитектура должна явно описывать временное хранилище и его лимиты.

## 12. Управление FFmpeg и дочерними процессами

FFmpeg должен запускаться как дочерний процесс под контролем backend.

Использовать `tokio::process::Command` либо проверенную обёртку с эквивалентными гарантиями управления процессами.

Требования:

- Передавать аргументы отдельными элементами, не одной shell-строкой.
- Не позволять клиенту задавать произвольный executable path.
- Не позволять клиенту передавать произвольные FFmpeg options.
- Валидировать все input и output paths.
- Не передавать пользовательские строки через shell.
- Захватывать stdout и stderr с ограничением потребления памяти.
- Контролируемо обрабатывать FFmpeg progress, если используется progress reporting.
- Устанавливать startup timeout.
- Применять максимальное runtime policy, где это необходимо.
- Ограничивать число одновременно работающих FFmpeg-процессов.
- Завершать процесс при отмене, удалении сессии, expiration или shutdown сервиса.
- Сначала выполнять graceful termination.
- После установленного grace period принудительно завершать процесс, если он не остановился.
- Дожидаться завершения процесса и выполнять reap дочернего процесса.
- Не оставлять дочерние процессы после завершения сессии.
- Не запускать повторные FFmpeg-процессы для одной активной сессии при повторных HTTP-запросах, если это не предусмотрено архитектурой.
- Редактировать или исключать секреты и чувствительную информацию из логов.

### 12.1. Безопасное построение аргументов

FFmpeg arguments должны формироваться из внутреннего playback plan, проверенной конфигурации и разрешённых media metadata.

Клиент не должен определять:

- Произвольные FFmpeg flags.
- Путь к executable.
- Произвольные input и output paths.
- Параметры, позволяющие получить доступ к сторонним файлам.
- Произвольные протоколы и сетевые адреса.
- Команды, обходящие ограничения ресурсов или безопасности.

Не считать передачу аргументов через `Command` достаточной защитой, если сами аргументы позволяют обращаться к неразрешённым источникам или файлам.

### 12.2. stdout, stderr и progress

Не накапливать весь вывод FFmpeg в памяти.

Использовать ограниченный буфер stderr и контролируемое чтение stdout. Если stdout используется для передачи медиаданных, это должно быть отдельным явно спроектированным pipeline с backpressure и корректной отменой.

При достижении лимита диагностического буфера продолжать безопасно обслуживать процесс, если это необходимо для предотвращения блокировки pipe, но не хранить неограниченный объём вывода.

Progress reporting должен разбираться как структурированные данные с ограничениями на размер и частоту обновлений.

Не полагаться только на строковые сообщения stderr для определения состояния сессии.

### 12.3. Cancellation и graceful termination

При остановке сессии:

1. Запретить создание новой работы для этой сессии.
2. Отменить ожидающие операции source adapter и буферизации.
3. Остановить связанные задачи и запросы, которые больше не нужны.
4. Отправить FFmpeg сигнал корректного завершения в соответствии с платформой и способом запуска.
5. Дождаться завершения в пределах grace period.
6. При превышении grace period принудительно завершить процесс.
7. Дождаться завершения процесса и выполнить reap.
8. Завершить связанные задачи и освободить ресурсы.
9. Удалить временные файлы, которые больше не используются.
10. Перевести сессию в `stopped` только после выполнения требуемой очистки.

При ошибке очистки регистрировать ограниченную диагностику и не утверждать, что все ресурсы освобождены, если это не подтверждено.

### 12.4. Отключение клиента

Отключение одного клиента не должно автоматически останавливать сессию, если её использует другой авторизованный клиент.

Session manager должен явно определять:

- Владельца сессии.
- Допустимое число клиентов.
- Условия продления idle timeout.
- Поведение при отключении последнего клиента.
- Возможность повторного подключения.
- Правила остановки сессии.
- Поведение при истечении срока действия токена или сессии.

Не оставлять активные сессии бесконечно только потому, что backend не может достоверно определить отключение клиента.

## 13. Playback sessions и HTTP API

API должен предоставлять операции создания, получения состояния и остановки playback-сессии.

Минимальные операции:

- `create` — проверить источник и создать сессию.
- `status` — получить текущее состояние, безопасную диагностику и доступные сведения о playback.
- `stop` — запросить остановку сессии и освобождение ресурсов.

Фактические endpoint, схемы запросов, схемы ответов и коды ошибок должны быть согласованы с `API.md` и OpenAPI specification.

Не дублировать и не переопределять существующие API-контракты без согласованного изменения документации.

### 13.1. Создание сессии

Создание сессии должно:

- Проверять разрешённый тип источника.
- Проверять обязательные параметры и выбранный файл.
- Применять лимиты до создания тяжёлых фоновых операций.
- Создавать уникальный идентификатор сессии.
- Инициализировать состояние и время создания.
- Учитывать владельца и правила доступа.
- Применять ограничения на параллельные операции.
- Возвращать документированную информацию о состоянии сессии.
- Не выдавать сессию за готовую до появления playable output.

Если создание сессии завершается ошибкой, связанные задачи, временные директории и процессы должны быть остановлены или очищены.

### 13.2. Получение состояния

Status endpoint должен возвращать согласованное с API состояние сессии и необходимую клиенту информацию.

В зависимости от реализации и контракта допустимо предоставлять:

- Текущее состояние.
- Код и безопасное описание ошибки.
- Время создания.
- Прогресс буферизации, если источник позволяет его определить.
- Доступность начального сегмента.
- Выбранный playback mode.
- Поддержку seeking и его ограничения.
- Время последней активности.
- Безопасные диагностические сведения.

Не раскрывать внутренние peer addresses, секретные URI, абсолютные пути и чувствительные детали реализации.

### 13.3. Остановка сессии

Stop endpoint должен быть идемпотентным либо иметь чётко документированное поведение при повторном вызове.

Он должен инициировать:

- Отмену ожидающих операций.
- Завершение FFmpeg.
- Остановку загрузки источника, если она больше не нужна.
- Освобождение лимитов активных сессий.
- Очистку временных файлов после завершения операций.

Не сообщать об успешной полной очистке до подтверждения завершения процессов и выполнения требуемых cleanup-операций.

## 14. Resource limits и concurrency

Установить явные ограничения для:

- Одновременных playback-сессий.
- Одновременных source resolution операций.
- Одновременных FFmpeg-процессов.
- Памяти на сессию.
- Дискового пространства на сессию.
- Общего cache.
- Буферизации источника.
- Startup timeout.
- Resolve timeout.
- Idle-session expiration.
- Времени выполнения FFprobe.
- Времени запуска FFmpeg.
- Общего времени выполнения отдельных операций.
- Количества torrent-соединений, если поддерживается engine.
- Скорости загрузки и соединений, если поддерживается engine.
- Частоты HTTP-запросов.
- Параллельных запросов сегментов.
- Объёма логов и диагностических данных.

Не использовать неограниченные Tokio tasks или очереди для пользовательских workload.

При достижении лимита возвращать документированную ошибку, а не допускать исчерпания ресурсов NAS.

### 14.1. Поведение при исчерпании ресурсов

При достижении лимитов система должна:

- Не принимать дополнительную работу, превышающую допустимую concurrency.
- Не создавать FFmpeg-процесс до резервирования необходимых ресурсов.
- Не увеличивать cache выше установленного лимита.
- Не допускать бесконечного ожидания свободного ресурса.
- Освобождать зарезервированные ресурсы после ошибки или отмены.
- Возвращать понятную ошибку клиенту.
- Регистрировать ограниченную диагностическую информацию.

Не допускать ситуации, когда отменённая операция продолжает удерживать semaphore permit, слот FFmpeg или место в очереди.

### 14.2. Таймауты и TTL

Предусмотреть отдельные настройки для:

- Resolve timeout.
- Metadata timeout.
- Buffering timeout.
- FFprobe timeout.
- FFmpeg startup timeout.
- Graceful termination period.
- Максимального времени ожидания чтения источника.
- Idle-session timeout.
- TTL временных данных.

Значения должны быть конфигурируемыми и проверяться в тестах.

Idle timeout должен учитывать реальную модель использования сессии. Не завершать активный playback только из-за отсутствия запросов в интервале, который не согласован с поведением клиента.

При shutdown сервиса необходимо прекратить приём новой работы, отменить или завершить активные операции, дождаться дочерних процессов в установленный срок и выполнить доступную очистку.

## 15. Security и ограничения источников

- Принимать только типы источников, поддерживаемые зарегистрированными source adapters.
- Валидировать magnet URI и другие source identifiers.
- Не создавать универсальный endpoint для произвольного URL fetching.
- Защищаться от SSRF, path traversal, некорректных медиафайлов и resource exhaustion.
- Не передавать source strings через shell.
- Не раскрывать внутренние peer addresses, credentials и raw source metadata без необходимости.
- Не обходить CAPTCHA, authentication, paywalls или anti-bot protections.
- Не считать доступность источника подтверждением права на его использование.
- Поддерживать законные источники, к которым пользователь имеет право доступа.
- Не допускать произвольного чтения локальных файлов через подмену input path.
- Ограничивать доступ к playlist и сегментам правилами владения сессией или access token.
- Не принимать клиентские filesystem paths.
- Не позволять клиенту управлять произвольными FFmpeg options.
- Ограничивать размер входных параметров и metadata.
- Учитывать некорректные или специально сформированные медиафайлы.
- Не допускать неограниченного потребления CPU, памяти, диска и сетевых соединений.
- Не записывать секреты в логи и диагностические endpoint.

### 15.1. Source validation

Source validation должна выполняться до запуска ресурсоёмких операций.

Backend должен проверять, что источник соответствует одному из поддерживаемых типов и что его параметры могут быть безопасно переданы соответствующему adapter.

Не считать любую строку, похожую на magnet URI или URL, допустимым источником.

Source adapter должен быть ответственен за ограничения конкретного типа источника, а HTTP API не должен предоставлять универсальный доступ к произвольным сетевым ресурсам.

### 15.2. Изоляция и filesystem

Все временные данные должны находиться в выделенной директории с ограниченными правами.

Идентификаторы сессий и имена сегментов не должны позволять выходить за пределы соответствующей директории.

Не использовать необработанные клиентские строки для построения filesystem paths.

При наличии отдельного torrent-компонента или worker-процесса необходимо определить границы доступа к файловой системе, сетевым ресурсам и процессам.

## 16. Observability и диагностика

Предоставлять безопасную диагностическую информацию через логи и, при необходимости, health или diagnostics endpoint.

Полезные метрики:

- Количество активных playback-сессий.
- Количество активных source resolution операций.
- Количество активных FFmpeg-процессов.
- Время создания сессии.
- Startup latency.
- Time-to-first-playable-segment.
- Time-to-first-frame, если он измеряется.
- Время буферизации.
- Время разрешения источника.
- Таймауты source adapter.
- Ошибки получения данных.
- FFmpeg exit code.
- Выбранный playback mode: stream copy, remux, VA-API или software.
- Успешность инициализации аппаратного ускорения.
- Причина отказа VA-API или fallback.
- Объём используемого cache.
- Ошибки остановки и очистки процессов.
- Ошибки очистки временных файлов.
- Число ошибок и таймаутов сессий.

Не логировать bearer tokens, credentials, секретные URL и полные magnet URI по умолчанию.

Логи должны помогать различать источник ошибки, не раскрывая чувствительные данные.

### 16.1. Диагностика playback mode

Для каждой сессии сохранять безопасные сведения о выбранном режиме:

- Stream copy / remux.
- Software transcoding.
- VA-API processing.
- Причина выбора режима.
- Причина fallback.
- Код завершения FFmpeg.
- Причина ошибки, если операция завершилась неудачно.

Не маркировать сессию как hardware-accelerated только по конфигурации `HWACCEL_MODE`. Отражать фактически выполненный режим.

### 16.2. Метрики производительности

Измерять startup latency и buffering отдельно, чтобы выявлять узкие места:

- Разрешение источника.
- Получение metadata.
- Ожидание доступных torrent-частей.
- Инспекция FFprobe.
- Запуск FFmpeg.
- Создание playlist.
- Создание первого сегмента.
- Доставка сегмента клиенту.

Собирать показатели без необходимости сохранять секретные идентификаторы источников или полные URI.

## 17. Android TV и клиентская совместимость

HLS является первоначальным кандидатом для web playback, но его совместимость должна проверяться отдельно для каждого целевого клиента.

Для Android TV необходимо проверить:

- Поддерживаемые видео- и аудиокодеки.
- Поддерживаемые профили и уровни кодеков.
- Pixel format и bit depth.
- Максимальное поддерживаемое разрешение.
- Поддерживаемые варианты HLS playlist.
- Поддерживаемый формат сегментов.
- Совместимость аудиопотоков и channel layout.
- Поведение при смене аудиодорожки.
- Поддержку seeking.
- Поведение при временной недоступности сегментов.
- Восстановление после остановки и повторного подключения.
- Реальное время до первого кадра.

Не считать успешное воспроизведение в браузере доказательством совместимости с Android TV.

Если конкретный клиент не поддерживает исходный кодек или контейнерный вариант, playback planner должен выбрать совместимый путь обработки, если он разрешён и укладывается в ресурсные ограничения.

## 18. Обязательный PoC и acceptance criteria

Streaming subsystem считается готовым к следующему этапу, когда тестами подтверждены следующие пункты.

### 18.1. Torrent и source adapter

1. Получение metadata для разрешённого тестового torrent.
2. Перечисление файлов и детерминированный выбор файла.
3. Чтение данных до полной загрузки файла.
4. Приоритизация выбранного файла, если поддерживается engine.
5. Буферизация, достаточная для начала playback.
6. Random access и seeking там, где engine заявляет их поддержку.
7. Корректная обработка отсутствующих и медленных peers.
8. Отмена чтения и прекращение ненужной загрузки после stop.
9. Ограничение cache и других ресурсов.
10. Подтверждённое поведение при завершении и ошибке источника.

### 18.2. Media processing

11. FFprobe успешно инспектирует поддерживаемый локальный тестовый файл.
12. MP4 и MKV проверены отдельно.
13. Совместимый источник может передаваться без ненужного transcoding.
14. Remux в HLS работает для выбранного совместимого тестового материала.
15. Требуемый transcode работает в software mode.
16. Требуемый transcode работает через VA-API на поддерживаемом тестовом хосте.
17. Software fallback работает, когда VA-API недоступен и strict mode отключён.
18. Strict mode выдаёт понятную ошибку, когда требуемое аппаратное ускорение недоступно.
19. Хост без `/dev/dri` может работать в software mode.
20. Ошибки FFprobe и FFmpeg корректно отражаются в состоянии сессии.

### 18.3. HLS и playback

21. Initial HLS playlist и playable segment становятся доступны в пределах настроенного timeout для валидного тестового источника.
22. Готовность сессии подтверждается доступностью валидного сегмента, а не только запуском процесса.
23. Клиент может получить playlist и готовые сегменты через HTTP API.
24. Запрос ещё не готового сегмента обрабатывается контролируемо.
25. HLS playlist соответствует выбранной стратегии доставки.
26. Time-to-first-frame измеряется на тестовом клиенте.
27. Seeking работает в пределах возможностей, заявленных source adapter и streaming pipeline.
28. Ошибка источника не приводит к бесконечной буферизации.
29. Проверены audio compatibility и ограничения субтитров.
30. Android TV проверен отдельно на выбранном тестовом устройстве или согласованной тестовой конфигурации.

### 18.4. Sessions и lifecycle

31. Создание сессии проходит через документированные состояния.
32. Status endpoint возвращает актуальное и корректное состояние.
33. Stop завершает связанные дочерние процессы.
34. Повторный stop обрабатывается согласно контракту API.
35. Idle timeout завершает неактивные сессии по настроенной политике.
36. Expired sessions и временные данные очищаются.
37. Shutdown сервиса запускает контролируемое завершение активной работы.
38. Ошибки cleanup не приводят к ложному сообщению об успешной полной очистке.
39. Повторные запросы не создают дублирующие FFmpeg-процессы для одной сессии, если это не предусмотрено архитектурой.

### 18.5. Ресурсы и безопасность

40. Параллельное воспроизведение остаётся в пределах настроенных лимитов.
41. Исчерпание ресурсов приводит к документированной ошибке.
42. Cache не превышает установленные ограничения.
43. Некорректные source identifiers не позволяют выполнять произвольные сетевые запросы.
44. Клиент не может получить произвольный локальный файл через playlist или segment endpoint.
45. Клиент не может передать произвольные FFmpeg options или executable path.
46. Секреты не попадают в логи.
47. Ошибки и таймауты не оставляют неконтролируемые процессы и фоновые задачи.
48. Временные данные после перезапуска сервиса обрабатываются по установленной cleanup policy.

### 18.6. Результаты PoC

Для каждого теста сохранять:

- Конфигурацию окружения.
- Версию torrent engine.
- Версию FFmpeg и FFprobe.
- Модель GPU и версию драйвера, если используется VA-API.
- Формат и характеристики тестового файла.
- Выбранный playback mode.
- Время до первого playable segment.
- Time-to-first-frame, если измеряется.
- Использование памяти и диска.
- Результат seeking.
- Поведение при stop и cleanup.
- Результат теста и выявленные ограничения.

Не отмечать критерий как выполненный на основании предположения или наличия соответствующей настройки. Требуется воспроизводимый результат тестирования.

## 20. Границы реализации и порядок работ

Реализовывать streaming subsystem поэтапно, чтобы не смешивать неподтверждённые возможности разных компонентов.

Рекомендуемый порядок:

1. Выбрать torrent engine через ADR и PoC.
2. Подтвердить чтение данных, выбор файла, буферизацию и random access.
3. Реализовать source adapter с отменой операций и контролем ресурсов.
4. Подтвердить работу FFprobe с выбранной моделью доступа к данным.
5. Реализовать playback planner для stream copy, remux и transcoding.
6. Проверить HLS на локальных тестовых файлах.
7. Проверить VA-API и software fallback.
8. Интегрировать torrent source с FFmpeg и HLS.
9. Реализовать session lifecycle и HTTP API.
10. Добавить seeking в пределах подтверждённых возможностей.
11. Добавить cleanup, resource limits и observability.
12. Выполнить интеграционные тесты с медленными и недоступными peers.
13. Проверить web playback и Android TV отдельно.
14. Отдельно провести PoC для строгого режима без записи медиа на диск, если он требуется.

Не считать streaming subsystem завершённым, пока не подтверждены не только старт воспроизведения, но и отмена, cleanup, обработка ошибок, ограничение ресурсов и поведение при длительной недоступности источника.

Все публичные endpoint, состояния сессий, коды ошибок и ограничения должны соответствовать `API.md` и OpenAPI specification.
