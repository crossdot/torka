# AGENT.md — инструкции агенту

## Обязательный этап Discovery

До написания существенного кода:

1. Изучить весь пакет спецификаций: `PRODUCT.md`, `ARCHITECTURE.md`, `API.md`, `STREAMING.md`, `DOCKER_SYNOLOGY.md`, `SECURITY.md`, `PROVIDERS.md`, `WEB_UI.md`, `CLIENTS.md`, `TESTING.md`, `IMPLEMENTATION_PLAN.md`, `DECISIONS.md`, `TASKS.md`.
2. Проверить репозиторий, существующий код, конфигурацию, зависимости, лицензии, тесты, Docker-образы и deployment-файлы. Если документ отсутствует, явно отметить это и опираться только на доступный контекст.
3. Проверить актуальные официальные документы Rust, Axum, Tokio, Serde, Vue, FFmpeg, Docker и выбранного source/torrent engine. Не предполагать API, сигнатуры, параметры или совместимость без проверки.
4. Уточнить целевую архитектуру Synology, CPU, версии DSM, доступность `/dev/dri`, драйверов и VA-API либо отметить это как блокер для аппаратного ускорения.
5. Проверить совместимость выбранного source/torrent engine с обнаружением метаданных, выбором файла, потоковым чтением, отменой, seek и произвольным доступом к данным.
6. Проверить, что выбранная стратегия FFmpeg поддерживает ожидаемые контейнеры, кодеки, seek и формирование HLS без предварительной загрузки всего медиафайла.
7. Подготовить ADR по torrent/source engine, streaming/seek, RuTracker/Rutor, Docker multi-arch, auth и раздаче frontend. Для существенных архитектурных решений фиксировать варианты, ограничения и последствия в `DECISIONS.md` или отдельном ADR.
8. Проверить лицензии прямых и транзитивных зависимостей, конфигурацию сборки FFmpeg и совместимость с планируемым распространением.
9. Выявить противоречия между спецификациями, реализацией и deployment. Не разрешать существенные противоречия молча.
10. Выдать краткий отчёт: подтверждённое, неизвестное, риски, противоречия, открытые вопросы и предлагаемые следующие шаги.

Не выдумывать доступность провайдеров, API, HTML-селекторы, credentials, результаты поиска, возможности source engine или совместимость оборудования.

## Правила реализации

- Rust stable; зафиксировать toolchain и версии существенных зависимостей.
- Axum, Tokio, Serde; `tracing` для логов.
- Разделять HTTP handlers, domain services, source adapters, playback orchestration и управление процессами.
- Использовать типизированные ошибки и единый формат API-ошибок.
- Не добавлять БД, Redis, очереди или микросервисы без документированного требования и ADR. Для MVP предпочитать состояние сессий в памяти и ограниченное временное хранилище.
- Провайдеры реализовывать через trait или эквивалентный интерфейс и статический registry. Не использовать динамические Rust-плагины в MVP без отдельного обоснования.
- Внешние провайдеры должны иметь явные timeout, лимиты размера ответа, ограничение параллелизма и частичную обработку ошибок.
- Внешние данные, URL, redirects, метаданные и содержимое медиа считать недоверенными.
- Валидировать все публичные входные данные. Ограничивать протоколы, URL, redirects, файловые пути, время выполнения, память, конкурентность и временное хранилище.
- Не обходить CAPTCHA, авторизацию, paywall, антибот-защиту или иные технические ограничения сайтов.
- Не использовать произвольные пользовательские FFmpeg options или shell-конкатенацию.
- FFmpeg запускать отдельным процессом через API управления дочерними процессами с отдельными валидируемыми аргументами.
- Контролировать stdout/stderr, timeout, cancellation, завершение и reap процессов. Не допускать блокировки Tokio executor синхронными операциями.
- Отслеживать все процессы, созданные playback session. Завершать их при stop, cancellation, expiry, ошибке и shutdown приложения.
- Не логировать cookies, токены, credentials, полный magnet URI, секретные URL или чувствительные данные провайдера.
- Любой cache должен иметь TTL, лимит размера и безопасную очистку.
- Не оставлять placeholder secrets, фиктивные реализации или TODO-only код, выдаваемый за готовую функциональность.
- Изменения держать небольшими, проверяемыми и совместимыми с существующими соглашениями проекта.

## API и совместимость клиентов

- `API.md` и OpenAPI schema — публичный контракт API.
- Публичные endpoints версионировать, первоначально под `/api/v1`.
- Использовать стабильные идентификаторы, документированные состояния и переходы playback sessions.
- Не публиковать внутренние Rust structs напрямую без осознанного решения.
- Документировать аутентификацию, авторизацию, ошибки, ограничения и примеры запросов.
- Основные операции API не должны зависеть от cookies браузера, состояния Vue или frontend-specific headers.
- Не раскрывать внутренние filesystem paths, process arguments, секреты и внутреннее состояние реализации.
- При breaking changes одновременно обновлять спецификацию, OpenAPI, примеры, тесты и все затронутые клиенты.
- Vue и будущий Android TV client должны использовать общий публичный API, а не зависеть от внутренних механизмов backend.

## RuTracker/Rutor и source adapters

- Проверить текущую доступность провайдеров и допустимые способы взаимодействия.
- Не обходить CAPTCHA, auth, paywall или антибот-защиту.
- Не хранить credentials без согласованного безопасного механизма.
- Если допустимая интеграция невозможна, оставить provider disabled/unavailable с диагностикой. Не выдавать фиктивные результаты.
- Не предполагать наличие undocumented API, стабильных HTML-селекторов или возможности прямого streaming.
- Парсеры тестировать на локальных фикстурах и mock responses.
- Предусмотреть обработку malformed responses, rate limiting, недоступности источника и upstream errors.
- Проверять схемы URL, redirects и конечные адреса согласно `SECURITY.md`.
- Провайдеры должны быть независимо тестируемыми и удаляемыми без нарушения остальной системы.
- Использовать законный контролируемый тестовый источник для первоначальной интеграции.

## Streaming и FFmpeg

- Следовать `STREAMING.md`.
- Не считать последовательный stdin pipe подходящим для произвольных MP4/MKV: проверить random access, seek и требования контейнера.
- Не загружать целиком медиафайл перед началом воспроизведения.
- Предпочитать stream copy/remux, если он действительно совместим с исходным потоком и целевым HLS.
- Транскодировать только при необходимости.
- Ограничивать время запуска FFmpeg, длительность процессов, stderr, количество процессов и буферы.
- Валидировать playlist и пути сегментов; исключать path traversal и произвольное чтение файлов.
- Не объявлять playback ready, пока не создан и не проверен корректный начальный воспроизводимый HLS segment.
- Обеспечить отмену, остановку, истечение сессии и очистку временных данных.
- Ограничивать размер временного хранилища и гарантировать очистку после завершения сессии.
- Проверять обработку ошибок, повреждённых медиафайлов, таймаутов и аварийного завершения FFmpeg.

## Intel VA-API и программный режим

- Основная цель аппаратного ускорения — Intel iGPU с VA-API на совместимом Linux host.
- Device path должен настраиваться; не предполагать, что каждый Synology предоставляет `/dev/dri`.
- Различать поддержку VA-API при сборке FFmpeg и фактическую доступность устройства во время выполнения.
- Проверять права доступа, инициализацию устройства и совместимость конкретного GPU, кодека, профиля, bit depth, разрешения и фильтров.
- Поддерживать режимы `auto`, `vaapi` и `software`.
- Реализовать и тестировать программный fallback, если он разрешён конфигурацией.
- При строгом требовании аппаратного ускорения не переключаться молча на software.
- Корректно сообщать фактически выбранный режим обработки.
- Не объявлять аппаратное ускорение работающим только на основании успешной сборки FFmpeg.
- Реальный VA-API test выполнять на совместимом host. До этого указывать, что аппаратный режим не подтверждён.
- Обеспечить работоспособность software mode без GPU и `/dev/dri`.

## Docker и Synology

- Следовать `DOCKER_SYNOLOGY.md`.
- Явно указывать поддерживаемые CPU architectures и проверять совместимость multi-arch образов.
- Фиксировать версии базовых образов и существенных зависимостей для воспроизводимых сборок.
- Включать необходимые компоненты FFmpeg и проверять их фактическую доступность в runtime.
- Не помещать секреты в image или repository.
- Использовать non-root user, где это возможно.
- Монтировать только необходимые каталоги и device nodes.
- Не использовать `privileged: true`, host networking, Docker socket или широкие filesystem mounts по умолчанию.
- Не хардкодить host group IDs в переносимый образ.
- Документировать ограничения конкретных NAS, DSM, архитектур и GPU.
- Проверять software mode независимо от наличия GPU.
- Не заявлять универсальную совместимость Synology без фактических подтверждений.

## Безопасность

Безопасность — обязательное условие выпуска. Следовать `SECURITY.md`.

- Валидировать каждый публичный API request.
- Защищать операции управления playback sessions аутентификацией и авторизацией.
- Использовать непредсказуемые идентификаторы сессий и проверять права доступа к каждой сессии.
- Защищать от SSRF, unsafe redirects, path traversal и произвольного чтения файлов.
- Ограничивать допустимые URL schemes и протоколы источников.
- Не передавать пользовательский ввод в shell и не разрешать произвольные FFmpeg arguments.
- Ограничивать частоту дорогих операций, конкурентность, время выполнения, размеры ответов, память и временное хранилище.
- Не отключать TLS verification как общее решение проблем соединения.
- Не ослаблять host permissions без обоснования и проверки последствий.
- Редактировать секреты и чувствительные данные в логах.
- Добавлять security tests при появлении новой границы безопасности.
- Не считать отсутствие обнаруженных проблем доказательством полной безопасности.

## Frontend

- Использовать Vue и выбранный проектом build tooling.
- Размещать API calls в отдельном client/service layer.
- Явно моделировать состояния loading, empty, ready, error и retry.
- Не помещать provider-specific scraping в frontend.
- Не раскрывать backend secrets.
- Не считать поведение браузерного плеера доказательством совместимости Android TV.
- Не использовать состояние Vue как источник истины для playback sessions.
- Сохранять совместимость frontend с публичным API и документировать способ раздачи frontend.
